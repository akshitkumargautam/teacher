Baremetal → Production Infrastructure

Setting up company infrastructure on a physical server using Proxmox, containers, automation, and orchestration

Virtualization Networking Containers Automation Orchestration

🎯 The Problem You're Solving

You have a physical computer (baremetal). You need it to run your company's staging and development environments — multiple isolated applications, databases, services, all reachable by your team, all reproducible.

Without any of the tools below, you'd be:

  • ❌ Installing everything directly on one OS — conflicts, no isolation, one bad install breaks everything
  • ❌ Manually SSHing in and running commands — no history, no reproducibility, "works on my machine" but not on staging
  • ❌ Configuring network rules by hand — one typo in iptables and nothing can talk to anything
  • ❌ No way to spin up a fresh environment — "just rebuild it from scratch" takes days

Each tool below solves one or more of these problems. The key insight: you're building layers of abstraction, each one making the layer above it simpler and more reliable.

🪪 Each Piece — What It Actually Is

Not just the name — the category, the type, and the one sentence that tells you what it fundamentally is.

Virtualization Proxmox VE
What is it?A web-based management platform for running virtual machines and containers on a physical server
TypeHypervisor management UI + API (wraps QEMU/KVM and LXC)
Runs asA complete Debian-based OS you install on baremetal (replaces your existing OS)
Why it existsWithout it, you'd manually manage QEMU/KVM via CLI — creating VMs by typing long commands, no dashboard, no snapshots UI, no clustering
AnalogyIf your server is a building, Proxmox is the building manager's office — it doesn't create the rooms (KVM does), but it lets you manage, monitor, and control them all from one place
Container Docker
What is it?A tool for packaging and running applications in isolated environments (containers) that share the host OS kernel
TypeContainer engine (CLI + daemon). Docker the company makes the tool. The actual runtime underneath is containerd
Runs asA background daemon (dockerd) you talk to via the docker CLI
Why it existsBefore Docker: "it works on my machine" — your app depends on specific library versions, OS settings, file paths. Docker packages ALL of that into a single image that runs identically everywhere
Not a VM!Containers are NOT virtual machines. They don't have their own kernel. They use Linux namespaces and cgroups to isolate processes while sharing the same kernel
AnalogyIf a VM is a separate house (own foundation, walls, roof), a container is an apartment — isolated living space, but shares the building's plumbing and electricity (kernel)
Networking Docker Networking
What is it?Docker's built-in system for letting containers talk to each other and to the outside world
TypeVirtual networking layer (creates virtual bridges, veth pairs, and iptables rules under the hood)
Key modesbridge (default, isolated network per host), host (no isolation, container uses host's network directly), overlay (spans multiple hosts — used by K8s/Swarm), none (no networking)
Why it existsContainers need network isolation (your app's port 8080 shouldn't collide with another's), but also need to talk to each other and the internet. Docker networking creates virtual networks that handle this automatically
AnalogyEach Docker network is like an internal office phone system — everyone inside can call each other by name, but calling the outside world goes through a central switchboard (NAT)
Automation Ansible
What is it?A tool that automates the configuration of machines — installs software, edits config files, restarts services, all from one control machine
TypeConfiguration management / automation tool (agentless — uses SSH to reach target machines, no software to install on them)
Runs asA CLI tool on your machine. You write YAML playbooks describing what state you want, and Ansible makes it happen
Why it existsWithout it: SSH into 10 machines, run the same 20 commands on each, hope you didn't typo on machine 7. With Ansible: write it once, run it everywhere, get the same result every time
Key ideaIdempotent — running a playbook twice gives the same result as running it once. It doesn't "install nginx again," it checks "is nginx installed?" and skips if yes
AnalogyAnsible is like a recipe for your server — "ensure these ingredients are present, in these quantities, combined this way." You can hand the recipe to a new chef (new server) and get the same dish
Automation OpenTofu
What is it?A tool for declaring and provisioning infrastructure resources — VMs, networks, storage, DNS records — from code
TypeInfrastructure as Code (IaC) provisioning tool. Open-source fork of Terraform
Runs asA CLI tool. You write .tf files (HCL language) declaring what infra you want. It figures out the diff and makes changes
vs AnsibleOpenTofu creates the infrastructure (VMs, networks). Ansible configures what's on it (installs software, writes configs). They're complementary, not competing
Why it existsWithout it: click through Proxmox UI to create VMs, manually assign IPs, hope you documented what you did. With OpenTofu: your entire infrastructure is in Git, version-controlled, reviewable, reproducible
Key ideaDeclarative — you describe the desired end state, not the steps to get there. "I want 3 VMs" not "create VM 1, create VM 2, create VM 3"
AnalogyIf Ansible is a recipe (steps to follow), OpenTofu is an architect's blueprint — it shows what the building should look like, and the tool figures out how to build it
Orchestration K3s
What is it?A lightweight Kubernetes distribution — it manages your containers across machines: starts them, restarts them if they crash, routes traffic to them, scales them up/down
TypeContainer orchestrator (a simplified, single-binary packaging of Kubernetes)
Runs asA system service. One machine is the "server" (control plane), others are "agents" (workers). Single binary, starts in seconds
vs Docker ComposeCompose runs containers on one machine. K3s runs containers across multiple machines, handles failover, service discovery, rolling updates, and load balancing
Why K3s over K8sFull Kubernetes has ~20 components and needs serious resources. K3s bundles them into a single ~70MB binary. Perfect for edge/baremetal/resource-constrained setups
AnalogyDocker Compose is a team lead managing one team in one room. K3s is an operations manager across the whole office — it knows where everyone sits, reassigns people if someone's sick, and directs visitors to the right desk
Networking Core Networking Concepts
IP Address — A unique number assigned to every device on a network, like a postal address for data. e.g., 192.168.1.100
Subnet — A subdivision of a network. 192.168.1.0/24 means "all 256 addresses from 192.168.1.0 to 192.168.1.255." The /24 is the subnet mask — it defines the boundary
DNS — The phone book of the internet. Translates names (google.com) to IP addresses (142.250.80.46). Your infra will have internal DNS too
Bridge — A virtual network switch. When Proxmox or Docker creates a bridge, it's making a virtual "ethernet switch" that multiple VMs/containers can plug into
VLAN — Virtual LAN. Lets you split one physical network into separate logical networks. Your staging and dev environments can share the same cable but be isolated via VLANs
NAT — Network Address Translation. Lets multiple devices with private IPs share one public IP to reach the internet. Your home router does this
Firewall — Rules that control what traffic is allowed in/out. Typically implemented via iptables or nftables on Linux
SSH — Secure Shell. An encrypted protocol for remotely controlling machines via terminal. Ansible uses SSH under the hood. Uses public/private key pairs for authentication
TCP/IP — The fundamental protocols of the internet. TCP ensures reliable, ordered delivery of data. IP handles addressing and routing. Everything else is built on top of these

🔗 How They Connect — The Data Flow

When someone accesses your staging app, here's what happens:

🌍 Browser request → DNS resolves hostname → arrives at your server's public IP
🛡️ → Firewall checks if port is allowed
🔀 → NAT / port forwarding routes to correct VM
🌉 → Bridge in Proxmox delivers to VM's virtual NIC
🐳 → Docker bridge inside VM routes to correct container
📦 → Container's app process receives the request

Your automation flow:

🏗️ OpenTofu → creates VMs in Proxmox (via Proxmox API)
📜 Ansible → SSHes into VMs, installs Docker, configures networking
🐳 Docker Compose / ☸️ K3s → deploys your app containers

Key insight: OpenTofu handles the "what infrastructure exists" question. Ansible handles the "what's installed on it" question. Docker/K3s handles the "what's running on it" question. Three separate concerns, three separate tools.

⚠️ Common Confusions

❌ "Docker containers are like lightweight VMs"
✅ Containers are isolated processes, not machines. They share the host kernel. A VM has its own entire OS. This matters for security, performance, and understanding what "isolation" actually means
❌ "OpenTofu and Ansible do the same thing"
✅ OpenTofu creates/destroys infrastructure (VMs, networks). Ansible configures existing machines (installs software, writes files). OpenTofu says "make a VM." Ansible says "on this VM, install Docker"
❌ "K3s replaces Docker"
✅ K3s uses a container runtime (containerd) under the hood. It doesn't replace Docker — it orchestrates containers. You can even use both: Docker for building images, K3s for running them
❌ "Networking is just IP addresses"
✅ IP addresses are one layer. You also need: routing (how packets find their way), DNS (name → IP), firewall (what's allowed), NAT (private → public), bridges (virtual switches), and VLANs (network segmentation). These are all separate concepts that work together

🛤️ Suggested Learning Path

Learn in this order — each layer depends on the one before it:

1
Networking Fundamentals
IP addressing, subnets, DNS, TCP/IP, routing, NAT, firewalls. This is the foundation — everything else sits on top of the network
2
SSH & Remote Access
How SSH works, key-based auth, ssh-agent, tunnels. You need this before Ansible can work
3
Virtualization & Proxmox
What a hypervisor does, VMs vs containers, Proxmox networking (bridges/VLANs), storage, templates
4
Linux Fundamentals for Containers
Namespaces, cgroups, systemd. The kernel features that make containers possible
5
Docker Deep Dive
Images, layers, volumes, Docker networking (bridge/host/overlay), Compose, multi-stage builds
6
Infrastructure as Code (OpenTofu + Ansible)
Declarative vs imperative, state management, playbooks, providers, the plan-apply cycle
7
K3s / Kubernetes
Pods, services, ingress, deployments, namespaces. Only after you deeply understand containers and networking
